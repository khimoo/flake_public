# Tailscale で LAN の外からマシン間 SSH とリモートビルドを通す

自宅 LAN の外にいるラップトップから、デスクトップへの SSH 作業とリモートビルド（常設ビルダーと `--build-host`）を通すための構成。
使い方は [../howtouse/tailscale.md](../howtouse/tailscale.md) を参照。

設定ファイル:

- `modules/nixos/tailscale.nix` — 全ホストで tailscaled を有効にする（`common.nix` から読む）
- `modules/nixos/ssh.nix` — tailnet 経由の接続名 `<短縮名>-ts` を生成する
- `hosts/nixos-desktop/default.nix` — デスクトップを無操作でサスペンドさせない。RDP のポートを tailnet 側だけに開ける

## `.local` の接続名は LAN の外で使えない

`ssh desktop` の接続先は `nixos-desktop.local` で、これは mDNS で引く名前だ（[machine-ssh.md](./machine-ssh.md)）。
mDNS は同じ LAN セグメント内のマルチキャストでしか届かないので、別のネットワークでは `Could not resolve hostname` になる。
名前が引けたとしても、デスクトップのアドレスはルータ配下のプライベートアドレス（`192.168.11.0/24`）で、外から直接は届かない。

## 経路に Tailscale を選んだ

Tailscale は、参加したホスト同士を WireGuard のトンネルでつなぐ。
各ホストが外向きに調整サーバへ接続し、NAT を越えて直接の経路を張る。直接張れないときは Tailscale の中継サーバ（DERP）を経由する。
ルータの設定を変えずに、プライベートアドレスのデスクトップへ届く。

退けた案と理由:

- **ルータでポート 22 を転送する**: 外部サービスが要らない。代わりに sshd がインターネットに直接さらされ、グローバル IP か DDNS が必要になる。プロバイダが CGNAT なら転送自体ができない
- **headscale（調整サーバの自前運用）**: Tailscale 社にアカウントと端末の情報を預けずに済む。代わりに、外から届く常時稼働のサーバが別に要る。2 台の個人利用には見合わない

Tailscale を使う代償は、アカウントと端末のメタデータ（ホスト名、IP、接続時刻）が Tailscale 社の調整サーバに載ることだ。
通信の中身は WireGuard で端末間暗号化されるので、DERP を経由しても中継サーバからは読めない。

## 接続名は `.local` と `-ts` の二本立てにする

`ssh.nix` は、各ホストに対して二つの `Host` ブロックを生成する。

- `desktop` / `nixos-desktop` / `nixos-desktop.local` → `HostName nixos-desktop.local`（mDNS）
- `desktop-ts` → `HostName nixos-desktop`（MagicDNS の短縮名）

`.local` の接続名を tailnet の名前に置き換えなかったのは、LAN 内の接続を Tailscale に依存させないためだ。
置き換えると、tailscaled が止まっているときや tailnet から抜けているときに、同じ部屋のデスクトップにも繋がらなくなる。
常設のリモートビルダーだけは LAN 内でも `-ts` を使う。自宅と出先で同じエントリを使え、同じデスクトップを二重に数えずに済むからだ（[remote-build.md](./remote-build.md#接続先は-tailnet-の接続名desktop-tsにする)）。

名前解決を試して自動で切り替える案（`Match exec` で `.local` を引いてから tailnet に落とす）も退けた。
接続のたびに名前解決の待ちが入り、失敗したときにどちらの経路で落ちたかが分かりにくくなる。

`-ts` のブロックは `config.services.tailscale.enable` が真のホストでだけ生成する。
認証（`User` と `IdentityFile ~/.ssh/id_lan`）とホスト鍵の扱い（`accept-new`）は `.local` のブロックと同じ生成関数から出すので、二つがずれない。
known_hosts には `nixos-desktop.local` と `nixos-desktop` が別の行として入る。鍵は同じデスクトップのホスト鍵なので、初回の `accept-new` で受理される。

## MagicDNS の短縮名は openresolv 経由で引ける

`HostName nixos-desktop` は、tailscaled が `/etc/resolv.conf` に書き込む search ドメイン（`<tailnet 名>.ts.net`）で補われて引ける。
この構成で tailscaled が resolv.conf を書き換えられることを、ソースで確認した（tailscale 1.90.9、nixpkgs `b6018f8`）。

- tailscale の `net/dns/manager_linux.go` は、resolv.conf の先頭行 `# Generated by resolvconf` を見て openresolv 方式を選ぶ。このホストの resolv.conf は openresolv 3.17.0 が生成しており（先頭行で確認）、この条件に当たる
- openresolv 方式では `resolvconf -m 0 -x -a tailscale` を実行する（`net/dns/openresolv.go`）。`-x` は排他指定で、tailnet に入っている間は resolv.conf の nameserver が `100.100.100.100`（tailscaled 内の DNS）だけになる
- nixpkgs の tailscale モジュールは、`networking.resolvconf.enable` が真なら `resolvconf` を tailscaled の `PATH` に入れる

帰結として、tailnet に入っている間は、そのホストの DNS 問い合わせがすべて `100.100.100.100` を経由する。
tailnet 外の名前は、tailscaled が元の上流（ルータの `192.168.11.1` など）へ転送する。
これが問題になったら `sudo tailscale set --accept-dns=false` で書き換えを止める。代わりに短縮名が引けなくなるので、`ssh.nix` の `-ts` の `HostName` を `<ホスト名>.<tailnet 名>.ts.net` にする必要がある。tailnet 名はアカウントごとに違う値なので、そのときは設定から注入する。

nixos-desktop で `tailscale up` した後、resolv.conf が `search <tailnet 名>.ts.net` と `nameserver 100.100.100.100` だけになったことを確認した（2026-09-23）。
同じ日に、別のホストからも短縮名を引けた（spin713 で `getent ahostsv4 nixos-desktop`、nixos-desktop で `getent ahostsv4 nixos-spin713` がどちらも `100.` で始まるアドレスを返し、`ssh spin713-ts` が通った）。spin713 をテザリングにつないだ状態（LAN の外）からも、`ssh desktop-ts` と `tailscale ping nixos-desktop` が通った。自分のホスト名は nss-myhostname がローカルのアドレスで答えるので、確認には相手のホスト名を `getent ahostsv4` で引く。`getent hosts` は IPv6 を先に引くので、tailnet の IPv6 アドレス（`fd7a:115c:a1e0:` で始まる）が表示される。

## SSH は openssh と `id_lan` のまま使う

Tailscale には独自の SSH サーバ（`tailscale up --ssh`）があり、tailnet の認証だけでログインを許可できる。これは使わない。
既存の openssh と LAN 共通鍵（`id_lan`）で認証が足りており、Tailscale SSH を足すと認証の経路が二つになる。
tailnet 経由でも sshd の `PasswordAuthentication = false` と `authorized_keys` がそのまま適用される。

sshd は `openFirewall = true` なので、ポート 22 は `tailscale0` を含む全インタフェースで開いている。tailnet 用に追加のファイアウォール設定は要らない。

## UDP 41641 を開け、reverse path filter は strict のままにする

`services.tailscale.openFirewall = true` で、tailscaled の待ち受けポート（UDP 41641）をホストのファイアウォールで開ける。
相手側から来た UDP を受けられると直接の経路が張れる場面が増え、DERP を経由せずに済む。

`networking.firewall.checkReversePath` は NixOS の既定の strict のまま。
nixpkgs のモジュールが loose に変えるのは `useRoutingFeatures` が `client` か `both` のとき（exit node やサブネットルートを使う場合）だけで、ホスト同士の通信には要らない。
exit node を使うことにしたら、`useRoutingFeatures = "client"` を足す。

## デスクトップは無操作でサスペンドさせない

外出中にデスクトップがサスペンドすると、tailnet からは起こせない。Wake-on-LAN は同じ LAN 内から送る必要があり、自宅に常時稼働の別機がないからだ。

- `services.displayManager.gdm.autoSuspend = false`: GDM のログイン画面は既定で無操作時にサスペンドする。nixpkgs の `gdm.nix` によると、この設定が適用されるのはログイン画面だけだ。再起動後にログイン画面のまま放置された場合に備える
- `extraGSettingsOverrides` で `sleep-inactive-ac-type='nothing'`: ログイン中のセッションの既定値を変える。ユーザーが GNOME の設定で選んだ値はこちらより優先されるので、手動でサスペンドを有効にすればそれに従う

停電後に電源を自動で入れるかどうかは BIOS の設定（AC 復電時の動作）で決まり、この repo の管理外だ。

## 出先のリモートビルドでは `--use-substitutes` を付ける

nixos-rebuild-ng（nixpkgs `b6018f8`）は、`--use-substitutes` を `nix-copy-closure -s` として渡す（`nixos_rebuild/__init__.py` と `nix.py` の `copy_closure`）。
ビルド結果をデスクトップから取り込む `nix-copy-closure --from` で `-s` を付けると、binary cache にあるパスは手元のラップトップが cache.nixos.org から直接取る。tailnet を通るのは、デスクトップでしか作れなかったパスだけになる。
自宅回線の上りや DERP 経由の経路は、cache.nixos.org への経路より遅いことが多い。

## GUI の確認は RDP でデスクトップの画面ごと使う

Bevy のゲーム（例: `~/sagyo/aquaponics-sim` の `just run`）はウィンドウを開くので、SSH のセッションだけでは表示先がなく起動に失敗する。
GNOME のリモートデスクトップ（RDP）を使うと、シミュレーションも描画もデスクトップの GPU で動き、tailnet には画面の映像と入力だけが流れる。

退けた案と理由:

- **waypipe**（Wayland のウィンドウを SSH で転送する）: aquaponics-sim の Bevy 0.14.2 は既定 features のままで、`x11` は含むが `wayland` は含まない。ウィンドウは XWayland 経由で開くので、Wayland のプロトコルを中継する waypipe では転送できない
- **X11 転送（`ssh -X`）**: GPU の描画結果をネットワーク越しの X サーバへ送ることになり、実用的な速度は出ないと見ている（未計測）

RDP のサーバ（`gnome-remote-desktop`）は GNOME を有効にした時点で入っている。repo で足したのは、サービスを有効にする設定とファイアウォールの設定だ。

- `systemd.services.gnome-remote-desktop.wantedBy = [ "graphical.target" ]`: gnome-control-center 49.5 は、システム側の `gnome-remote-desktop.service` の UnitFileState が `enabled` か `disabled` のときだけ、設定 → システムに「リモートデスクトップ」を出す（`panels/system/cc-system-panel.c` と `cc-systemd-service.c`）。nixpkgs のモジュールはユニットを `systemd.packages` で置くだけなので、状態が `linked` になって項目が隠れる。実際に nixos-desktop で項目が出なかった（2026-09-23）。ユニットの `[Install]` にある `WantedBy=graphical.target` と同じ先に繋ぐと `enabled` になる。nixpkgs の unstable（`ef34387`）と master のモジュールにも同じ設定は無い（2026-09-23 時点）。モジュールが有効にするようになったら、この設定は消す

- `networking.firewall.interfaces.<tailscale0>.allowedTCPPortRanges` に 3389〜3399 を入れる。インタフェースを限定しているので、LAN 側とインターネット側には開かない。RDP の認証はパスワードだけなので、tailnet の外からは届かないようにしておく
- 範囲にしたのは、gnome-remote-desktop 49.2 の gsettings スキーマで `negotiate-port` が既定で真だからだ。設定したポート（既定 3389）が使用中なら、後続の 10 ポートから空きを探す。Remote Login（ログイン画面から新しいセッションを始める）と Desktop Sharing（ログイン中のセッションを共有する）を両方有効にすると、後から起動した側が 3390 以降にずれる

RDP の有効化とパスワードは GNOME の設定で行い、repo には置かない（手順は [../howtouse/tailscale.md](../howtouse/tailscale.md)）。

画面をロックした状態や、再起動後に誰もログインしていない状態で繋がるかは、実機では未確認。
ログイン中のセッションを共有する Desktop Sharing は、誰もログインしていなければ使えない。Remote Login はログイン画面から入れるが、同じユーザーのセッションが手元に残っているときの挙動は確かめていない。

## ノード鍵の期限はデスクトップで切っておく

Tailscale のノード鍵は既定で 180 日で期限が切れ（[Tailscale のドキュメント](https://tailscale.com/kb/1028/key-expiry)）、期限後は再認証するまで tailnet から外れる。
デスクトップで再認証するにはブラウザ操作が要るので、外出中に期限が来ると戻るまで繋がらない。
admin console の Machines ページで、デスクトップの鍵の期限を無効にする（Disable Key Expiry）。
ラップトップは手元で再認証できるので、期限を残してよい。

## セキュリティ上の判断

tailnet に参加したホストの sshd は、tailnet 内の全ノードから届く。
個人の tailnet に自分の 2 台だけを入れている間は、既定の ACL（自分の端末同士はすべて通す）で足りる。ログインには引き続き `id_lan` が要る。
他人の端末や仕事用のマシンを tailnet に入れるなら、先に ACL でタグを設計し、sshd に届くノードを絞る。

## 見直す条件

- resolv.conf の書き換えが問題になったら、前述の `--accept-dns=false` と FQDN の組み合わせに移る
- DNS を systemd-resolved に移したら、tailscaled は resolved 方式を選ぶ。`getent hosts nixos-desktop` で短縮名が引けるかを確かめ直す
- tailnet に自分以外の端末を入れるなら、ACL を先に設計する。RDP はパスワード認証なので、tailnet 内の端末すべてから届く状態のままにしない
