# 規則を守らせる仕組み（confgen）

規則: [flake_public のあるべき姿](rules.md)
使い方: [confgen.md](../howtouse/confgen.md)

confgen は、[flake_public のあるべき姿](rules.md) の規則 A と規則 B を守らせる生成器である。
コンポーネント定義（`config/elements/*.star`）とホストのファイル（`config/hosts/*.toml`）を読み、ホストごとの構成を作る。

コンポーネントどうしの関係は、コンポーネント定義の外に宣言しない。
定義の外に「どの設定がどの利用目的のためか」を別に宣言する形（以前の `local.relations`）は退けた。宣言と実際の設定の参照がずれても止まらず、基盤（Neovim）が機能（sshfs）の有無を調べて分岐していた。

## 言葉と confgen の対応

| 言葉 | confgen での書き方 |
|---|---|
| コンポーネント | `config/elements/*.star` の1ファイルがコンポーネント定義1つにあたる。ファイル名がコンポーネントの名前になる |
| ユーザー | ホストのファイルの `[[users]]` の1項目 |
| 利用目的 | `[[users]]` の `purposes` に挙げたコンポーネント |
| ハードウェアプロファイル | ホストのファイルの `machine` に書いたコンポーネント（`kind = "machine"`） |
| プラットフォームの事実 | `kind = "machine_fact"` のコンポーネント。ハードウェアプロファイルが `requires` に挙げたものが、そのホストで成り立つ |
| 十分条件 | ほかのコンポーネントは `requires` と、関数の仮引数（参照する相手、寄与する相手）。プラットフォームの事実は `needs` |
| 有効 | confgen はユーザーごとに、`purposes` のコンポーネントとハードウェアプロファイルから十分条件のつながりをたどり、行き着いたコンポーネントの集合を求める |
| ホストに入る | どれかのユーザーについて有効なコンポーネント |
| 公開値 | `public` が返す値 |
| 参照 | 関数の仮引数でコンポーネント Y を受け、Y の公開値を読む |
| 寄与、寄与値 | `writes` の仮引数でコンポーネント Y を受け、`write(Y, 値)` で Y に値を送る。`config` と `user_config` が option（`home.packages` など）に値を出すのも、option への寄与として扱う。複数のコンポーネントが同じ option に値を出し、NixOS のモジュールの仕組みが値を合わせるのは、寄与値の集約にあたる |
| システム設定 | `config` が返す NixOS の設定と、`nixos_imports` のモジュール |
| ユーザー設定 | `user_config` が返す Home Manager の設定と、そのユーザーだけの NixOS の設定（`users.users.<ユーザー>` の下など） |
| ユーザー依存の値 | `user` の値と、`public` がユーザー依存の値を読むコンポーネントの公開値（`checkout.root` など） |
| 外部コンポーネント | nixpkgs のパッケージと、nixpkgs、Home Manager、flake の入力のモジュール |

## コンポーネント定義に書くもの

十分条件はコンポーネント定義の中の式で決まり、ホストの `purposes` でもハードウェアプロファイルでも変わらない。

プラットフォームの事実を `requires` に挙げられるのは、ハードウェアプロファイルとほかの事実だけである。
`requires` は confgen がコンポーネントを入れる関係なので、利用目的や道具が挙げると、利用目的を選んだだけで事実が成り立つことになり、「利用目的を選ぶ」と「ホストが何を持つか」が区別できなくなる。
利用目的や道具の十分条件にプラットフォームの事実を挙げるときは、`needs` に書く。
どのホストでどのコンポーネントを使うかは、ユーザーがホストごとに選ぶ `purposes` で決める。ホストの名前やプラットフォームの事実を条件にしてコンポーネントを足す書き方は持たない。ホストの名前を条件にすると、利用目的かハードウェアプロファイルを足すたびに、その組み合わせを人が見直すことになる（課題3）。

`needs` に挙げたプラットフォームの事実は、confgen が入れるのではなく確かめる十分条件の項目で、有効なコンポーネントを変えない。
有効なコンポーネントが決まった後で、そのコンポーネントがホストに入るとき、挙げた事実がそのホストで成り立つことを確かめ、成り立たなければ生成を止める。

二つのコンポーネントを組み合わせて初めて要るコンポーネント（sshfs 上の direnv の置き場所など）は、両方をたどる利用目的の `requires` に並べる（[rules.md](rules.md) の「組み合わせによる設定の扱い」）。

物理的な事実で決まらない、ホストごとの処理の違いは、ホストごとの担当として書かず、自分用サーバ（`run_home_server` を選んだホスト）とクライアント（サービスを使うユーザーの利用目的）に分ける。
担当として各ホストに書くと、利用目的とホストの組み合わせを人が管理することになる。
クライアントは接続先をどこにも書かず、`find_home_server` が `roles` から、`run_home_server` が有効なユーザーのいるただ 1 つのホストを求める。0 個か 2 個以上なら止める。
サーバのコンポーネントはサーバのホストの `purposes` とハードウェアプロファイルだけからたどるので、ほかのホストのクライアントがなくなっても、サーバのコンポーネントは残る（[rules.md](rules.md) の「扱っていない課題」）。

プラットフォームの事実や `serve_workspace` のように、設定値を出さず、十分条件をつなぐだけのコンポーネントもある。設定値を出す関数を持たないので、空の出力の検査の対象にならない。

`host.users` と `machines` からは `purposes` と `machine` を外して渡す。コンポーネントが、どのコンポーネントが有効かを値として読み、値で分岐できないようにするため。

`owner` は `config/owner.toml` の値で、リポジトリの持ち主の Git identity、エージェント設定の場所、秘密の配置先、LAN の公開鍵を持つ。
どのホストのどのユーザーについても同じ値なので、`config` からも読める。
ユーザーに入るのは、`owner` を読むコンポーネントがそのユーザーについて有効なときだけなので、持ち主の値を誰に入れるかは `purposes` で決まる。
ユーザーの名前と同じ名前のファイル（`config/users/<名前>.toml`）から読む形は退けた。値が入るかどうかがユーザーの名前で決まり、ホストをまたいで同じ人を表すために、名前を各所に書いて手で合わせることになる。持ち主は 1 人だけで、2 人目の個人の値は表せない。

`roles` は、役目のコンポーネント（`role = True`）が有効なユーザーを、全ホストについて渡す。
有効なコンポーネントは値を使わずに `purposes`、`requires`、ハードウェアプロファイルから決まるので、confgen は全ホストについて有効なコンポーネントを先に求めてから、コンポーネントの関数を呼ぶ。
`purposes` そのものは渡さない。`purposes` は十分条件をたどる起点で、役目のコンポーネントが有効かどうかはたどった結果である。
`roles` を読むコンポーネントが、値を見て設定値をすべて空にすると、空の出力の検査で止まる（規則 A の4つめ）。
ホストの TOML に、役目を持つユーザーの名前（`ssh_user`、`build_host`、管理者のユーザーなど）を書く形は退けた。役目はユーザーの `purposes` で決まるので、同じ事実を値でも書くと、食い違っても confgen が止められない。

`roles` を読む側は、ほかのホストの `purposes` が変わると生成結果が変わる。`confgen affected` は、変更されたコンポーネントが役目のコンポーネントに行き着くとき、`roles` を読むコンポーネントとそのホストも対象に含める。

`config` はホストごとに1回、`user_config` はコンポーネントが有効なユーザーごとに1回呼ぶ。
`public` と `writes` は、ユーザー依存の値を読むかどうかを仮引数から求め、読むならユーザーごとに、読まないならホストごとに1回呼ぶ。

ユーザーごとの NixOS の設定は、システム設定と同じ NixOS の構成に入る。ユーザー A とユーザー B が同じ option に別の値を出すと、NixOS のモジュールの仕組みが合わせるか、評価が衝突のエラーで止まる。

## 守らせ方

[rules.md](rules.md) の規則を、confgen は次のように守らせる。括弧の中は守らせ方の種類で、強い順に、書けなくする、ツールが代わりに行う、実行前に検査する、実行結果を検査する、である。

### 有効・無効の決定（規則 A）

- 有効か無効かは、confgen が `purposes` とハードウェアプロファイルから十分条件のつながりをたどって求める。コンポーネント定義に有効か無効かを書く場所はない（ツールが代わりに行う）。
- 十分条件は、設定値を計算する前に読める。`requires` と `needs` はファイルの最上位に書く文字列の一覧で、関数の仮引数はコンポーネントの名前に限る。最上位に書けるのは `name = value` と、決まった名前の関数だけで、条件分岐や否定、ユーザーの指定を十分条件に書く構文はない（書けなくする）。
- 有効なコンポーネントの設定値だけを、confgen がホストとユーザーの構成に出す（ツールが代わりに行う）。
- `needs` のプラットフォームの事実を確かめ、成り立たなければ止める。`needs` にプラットフォームの事実でないコンポーネントを書くと止める（実行前に検査する）。
- 設定値を出す関数を持つコンポーネントが、有効なのに何も出さなければ止める。`config` か `writes` を持つコンポーネントがホストで何も出さないとき、`user_config` かユーザーごとの `writes` を持つコンポーネントがあるユーザーについて何も出さないときに、エラーにする。option は出すが中身が空（`home.packages = []`）の書き方は見つけられない（実行結果を検査する）。

### 値の流れ（規則 B）

規則 B は言語と confgen の検査で守らせる。Nix では守らせられない。Nix のモジュールは `config` 全体を読め、コンポーネントに `pkgs` を渡すとその中の関数でファイルを読めるため。

- Starlark にはファイル、環境変数、時刻を読む手段が無い。confgen は `load` を止め、コンポーネントに渡す組み込みの名前を `write`、`struct` とNixの値を指定するヘルパー（[使い方](../howtouse/confgen.md)の表）に限る（書けなくする）。
- ホストとユーザーの情報（system、ユーザー名、home と、TOML の値）は、confgen が `host` と `user` として値で渡し、全ホストの TOML は `machines` として渡す。コンポーネントは外から読むのではなく、渡された値として読む（ツールが代わりに行う）。
- 参照する相手と寄与する相手は、関数の仮引数で宣言する。confgen は宣言された相手の値だけを渡す。仮引数の集合は、使われていない仮引数を止める検査で、本体の式が実際に指すコンポーネントと一致させる（ツールが代わりに行う）。
- 仮引数に挙げた相手は、十分条件に入る。参照する相手と寄与する相手は、必ず有効になる（ツールが代わりに行う）。
- 寄与は、有効なコンポーネントの `writes` だけを呼んで集める。無効なコンポーネントの寄与値は集まらない（ツールが代わりに行う）。
- `config` がユーザー依存の値を読むと止める。どのユーザーについてコンポーネントが有効になったかによって、システム設定が変わらないようにするため（実行前に検査する）。
- 公開値は凍結してから渡す。読んだ側が書き換えて、同じ値を読む別のコンポーネントの結果を変えることを防ぐ（書けなくする）。
- 公開値の読み合いが循環していたら止める（実行前に検査する）。
- 仮引数には、confgen が作るコンポーネントの値を渡す。Starlark の中では作れないので、`write` の相手は仮引数でしか指せない。この値を公開値や寄与値に入れて渡すことは止める。
- 寄与を受け取るコンポーネントは、受け付ける値の形を `accept` で宣言できる。宣言したコンポーネントへの `write` はキーワード引数だけを取り、confgen が `accept` を呼んで返り値を寄与値にするので、書き間違えた名前は寄与する側で止まる。`accept` は仮引数にコンポーネントを取らないので、ほかのコンポーネントの値を読めない。形の取り違え（`accept` の有無と `write` の形）は読み込み時に止める（実行前に検査する）。
- 評価の順は、`public`（読む相手の `public` が先）、`writes`、`config`（自分への寄与値を受け取る）。`public` は自分への寄与値を受け取れない。

規則 B を守らせられるのは `config/elements/` のコンポーネントの中だけ。Nix のモジュールとして残っている設定は、合わさった後の値を読めるので保証の外にある。

## 基本方針を選ぶ起点

統合 Home Manager のバックアップ拡張子と pkgs・パッケージ配置の方針は、NixOS の基本要素 `machine_base` が出す。単独 Home Manager で unfree パッケージを許可する場合は、その機械の基本要素から `home_base` を参照する。machine を省略した単独 HM のテストでは、必要な fixture の purposes に明示する。構成を接続するファイルから方針値を暗黙に注入しない。

## Nix との分担

confgen は Nix の評価中に build して実行し（import from derivation）、ホストごとの Nix ファイルを生成する。NixOS と Home Manager は、この同じ生成物の `nixos` と `homes.<ユーザー>` を実際に import する。表示専用の一覧や、同じ設定を管理する別台帳は作らない。

生成物は element 別の module と出所を保持する。パッケージやスクリプトなどのヘルパーは、Go が決まった Nix 式へ変換する。任意の Nix 式を渡す API は持たない。文字列と属性名は引用し、文字列中の `${…}` は Nix の式として実行されないようにする。型・既定値・優先順位・リストの合成は Nix に任せる。

外部 module の参照には提供元と属性の共通 key を付ける。複数の element が同じ module を使っても、その module の設定を二重に追加しない。どの element が要求したかは、各 element の import に残る。

`confgen why` は目的または machine から element への経路と、その element がホスト全体で出す option を表示する。option の一覧は全ユーザー分の合併であり、導出経路を指定したユーザーだけの一覧ではない。`confgen explain` と `affected` も同じ依存解析を使う。生成 Nix の `_file` も element を指すため、評価エラーから出所を追える。

値（ホストの構成、`purposes`、ホストとユーザーの値）は TOML に置き、処理はコンポーネント定義に置く。flake は評価の最初に構成の一覧を決める必要があり、Nix が読めるのは Nix、JSON、TOML だけなので、ホストのファイルは TOML にした。flake（`lib/configurations.nix`）は `config/hosts/*.toml` から構成の名前、system、ユーザーを読み、confgen は同じファイルをコンポーネントに渡す。同じ値を2か所に書かなくて済む。

ホスト名、system、ユーザー名は、`lib/configurations.nix` が import するときに渡す。NixOS のモジュールは生成 Nix の `nixos` を、Home Manager のモジュールは `homes.<ユーザー>` を使う。`config` や module 引数の `pkgs` から決めると、設定の名前の一覧を決めるのに設定そのものが要り、無限再帰になる。confgen の build には specialArgs の `inputs` の nixpkgs を使う。

この build もほかの build と同じく、`nixos-spin713` ではデスクトップに回る。macOS の Home Manager 構成では aarch64-darwin の confgen を build するので、Linux の `check.sh` からは評価できない。Mac を使い始めるまで、そのホストのファイルを置いていない。

## 変更が影響する範囲

`confgen affected <repo-root> <変更ファイル>...` は1行の JSON `{"elements": [...], "hosts": [...]}` を返す。`elements` は、変更したコンポーネント、その公開値を参照するコンポーネント、寄与先の名前。`hosts` は、それらを生成する実在ホストの名前。ホスト・ユーザーの情報を変更した場合は、それぞれ `host`・`machines`・`user` への影響として扱う。コンポーネントから影響を辿れない変更は `elements = ["ALL"]` とする。

[scripts/check.sh](../../scripts/check.sh) はこの結果と各 check の札を照合して、ホストの評価とテストのビルドを選ぶ。札と実行範囲は [検証ガイド](../howtouse/validation.md#checksh) を参照。

## 今後の課題

- [ ] 任せる側の `remote_build` が送るビルドの種類（`supportedFeatures`）を、引き受ける側の実際の設定から作る仕組み。今は `remote_build.star` の定数で、引き受ける側の `system-features` とは機械的に結ばれていない。`kvm` だけは、`serve_builds` の `needs = ["local_kvm"]` が、KVM のないホストを自分用サーバにしたときに生成を止める。KVM のないホストも `kvm` 抜きで自分用サーバにするには、confgen がほかのホストのプラットフォームの事実を `roles` と同じように渡す必要がある。
