# 規則 A と規則 B の実現（confgen）

規則: [flake_public のあるべき姿](rules.md)
使い方: [confgen.md](../howtouse/confgen.md)

confgen は、[flake_public のあるべき姿](rules.md) の規則 A と規則 B を、`config/elements/*.star` の要素と `config/hosts/*.toml` のホストのファイルで実現する。

部品どうしの関係は、要素の定義の外に宣言しない。以前は `local.relations` に「どの設定がどの目的のためか」を別に宣言していたが、宣言と実際の設定の参照がずれても止まらず、基盤（Neovim）が機能（sshfs）の有無を調べて分岐していた。

## 規則の言葉と confgen の対応

| 規則の言葉 | confgen での書き方 |
|---|---|
| 部品 | 要素。`config/elements/*.star` の1ファイルが要素1つにあたる |
| 利用者 | ホストのファイルの `[[users]]` の1項目 |
| 公理 | 利用者ごとに、`[[users]]` の `purposes` に挙げた要素の判定と、ホストのファイルの `machine` に書いた機体の要素（`kind = "machine"`）の判定 |
| 判定 | confgen は利用者ごとに、公理から推論規則をくり返し当てはめて、判定が真の要素の集合を求める。どれかの利用者について真の要素が、ホストに入る要素になる |
| 前件が1つの推論規則 | 参照。要素 X が要素 Y を参照すると、「要素 X の判定が真ならば、要素 Y の判定も真」になる。参照は、関数の仮引数（受け取る、渡す）と `requires`（値を読まずに使う）で書く |
| 前件が複数の推論規則 | 派生要素の `when`。「`when` に挙げた要素の判定がすべて真ならば、派生要素の判定も真」になる |
| 受け取る | 関数の仮引数で要素 Y を受け、要素 Y の `public` の値を読む |
| 渡す | `writes` の仮引数で要素 Y を受け、要素 Y に値を書き込む。`config` と `user_config` が option（`home.packages` など）に値を出すのも、option への書き込みとして扱う。複数の要素が同じ option に値を出し、NixOS のモジュールの仕組みが値を合わせるのは、渡すにあたる |
| ホスト全体の設定値 | `config` が返す NixOS の設定と、`nixos_imports` のモジュール |
| 利用者の設定値 | `user_config` が返す Home Manager の設定と、その利用者だけの NixOS の設定（`users.users.<利用者>` の下など） |
| 利用者によって変わる値 | `user` の値と、`public` が利用者によって変わる値を読む要素の公開値（`checkout.root` など） |
| 外から持ち込む部品 | nixpkgs のパッケージと、nixpkgs、Home Manager、flake の入力のモジュール |

参照は要素の定義の中の式で決まり、ホストの `purposes` では変わらない。

機体の事実（`kind = "machine_fact"`）は、機体の要素から導かれる部品で、機体の要素とほかの事実だけが参照できる。行動や道具が参照すると、行動を選んだだけで機体の事実が真になり、「行動を選ぶ」と「機体が何を持つか」が区別できなくなるため。機体によって変わる部品は、派生要素の `when` に行動と事実を挙げて導く。`when` に機体の要素は挙げられない。機体の名前を条件にすると、行動か機体を足すたびに、行動と機体の組み合わせを人が見直すことになる（要件 3）。

`needs` は推論規則ではなく、判定が済んだ後の検査で、判定を変えない。要素の判定が真の利用者について、挙げた要素の判定も真であることを確かめる。足りない事実を `requires` で補うと、機体が持たない事実が真になるので、検査として止める。

物理的な事実で決まらない、機体ごとの処理の違いは、機体ごとの担当として書かず、自分用サーバ（`run_home_server` を選んだホスト）とクライアント（サービスを使う利用者の行動と、その派生要素）に分ける。担当として各機体に書くと、行動と機体の組み合わせを人が管理することになる。クライアントは接続先をどこにも書かず、`find_home_server` が `roles` から、`run_home_server` が入っている利用者のいるただ 1 つのホストを求める。0 個か 2 個以上なら止める。サーバの判定はサーバのホストの公理だけから導くので、ほかのホストのクライアントがなくなっても、サーバの部品は残る（[rules.md](rules.md) の「扱っていない課題」）。

事実や `serve_workspace` のように、設定値を出さず、推論規則をつなぐだけの要素もある。設定値を出す関数を持たないので、空の出力の検査の対象にならない。

`host.users` と `machines` からは `purposes` と `machine` を外して渡す。要素が判定を値として読み、値で分岐できないようにするため。

`owner` は `config/owner.toml` の値で、リポジトリの持ち主の Git identity、エージェント設定の場所、秘密の配置先、LAN の公開鍵を持つ。どのホストのどの利用者についても同じ値なので、`config` からも読める。利用者に入るのは、`owner` を読む要素の判定がその利用者について真のときだけなので、持ち主の値を誰に入れるかは `purposes` で決まる。利用者の名前と同じ名前のファイル（`config/users/<名前>.toml`）から読む形は退けた。値が入るかどうかが利用者の名前で決まり、ホストをまたいで同じ人を表すために、名前を各所に書いて手で合わせることになる。持ち主は 1 人だけで、2 人目の個人の値は表せない。

`roles` は、役目の要素（`role = True`）の判定が真の利用者を、全ホストについて渡す。判定は値を使わずに `purposes`、`requires`、`when`、機体の要素から決まるので、confgen は全ホストの判定を先に求めてから要素の関数を呼ぶ。`purposes` そのものは渡さない。`purposes` は推論規則の入力で、役目の要素の判定は推論規則の結果である。`roles` を読む要素が、値を見て設定値をすべて空にすると、空の出力の検査で止まる（性質 1）。ホストの TOML に、役目を持つ利用者の名前（`ssh_user`、`build_host`、管理者の利用者など）を書く形は退けた。役目は利用者の `purposes` で決まるので、同じ事実を値でも書くと、食い違っても confgen が止められない。

`roles` を読む側は、ほかのホストの `purposes` が変わると生成結果が変わる。`confgen affected` は、変更された要素が役目の要素の判定につながるとき、`roles` を読む要素とそのホストも対象に含める。

`config` はホストごとに1回、`user_config` は要素が入る利用者ごとに1回呼ぶ。`public` と `writes` は、利用者によって変わる値を読むかどうかを仮引数から求め、読むなら利用者ごとに、読まないならホストごとに1回呼ぶ。`config` が利用者によって変わる値を読むと止める。どの利用者の判定で要素が入ったかによって、ホスト全体の設定値が変わらないようにするため。

利用者ごとの NixOS の設定は、ホスト全体の設定と同じ NixOS の構成に入る。利用者 A と利用者 B が同じ option に別の値を出すと、NixOS のモジュールの仕組みが合わせるか、評価が衝突のエラーで止まる。

派生要素は、どの要素からも参照できず、`purposes` にも挙げられない。派生要素の判定が真になるのを、`when` に挙げた要素がそろったときに限るため。このため、派生要素を後件に持つ推論規則は `when` の1つだけで、派生要素について「または」は書けない。参照される要素は複数の要素から参照できるので、前件が1つの推論規則どうしの「または」は書ける。

## 守らせ方

規則 B は言語と confgen の検査で守る。Nix では守れない。Nix のモジュールは `config` 全体を読め、要素に `pkgs` を渡すとその中の関数でファイルを読めるため。

- Starlark にはファイル、環境変数、時刻を読む手段が無い。confgen は `load` を止め、要素に渡す組み込みの名前を `write`、`struct` と印を作る関数（[使い方](../howtouse/confgen.md)の表）に限る。
- ホストとユーザーの情報（system、ユーザー名、home と、TOML の値）は、confgen が要素 `host` と `user` として渡し、全ホストの TOML は `machines` として渡す。要素がホスト名やフラグで分岐しなくて済むようにするため。
- 仮引数の集合は、使われていない仮引数を止める検査で、本体の式が実際に指す要素と一致させる。
- 仮引数には、confgen が作る要素の値を渡す。Starlark の中では作れないので、`write` の相手は仮引数でしか指せない。この値を公開値や書き込みの値に入れて渡すことは止める。
- 公開値は凍結してから渡す。読んだ側が書き換えて、同じ値を読む別の要素の結果を変えることを防ぐ。
- 評価の順は、`public`（読む相手の `public` が先）、`writes`、`config`（自分への書き込みを受け取る）。`public` は自分への書き込みを受け取れない。

規則 B を保証できるのは `config/elements/` の要素の中だけ。Nix のモジュールとして残っている設定は、合わさった後の値を読めるので保証の外にある。

要素が値を見て設定値をすべて空にする書き方（規則 A に反する）は、出力が空になったときに止める。`config` か `writes` を持つ要素がホストで何も出さないとき、`user_config` か利用者ごとの `writes` を持つ要素がある利用者について何も出さないときに、エラーにする。option は出すが中身が空（`home.packages = []`）の書き方は見つけられない。

## Nix との分担

confgen は Nix の評価の途中で build して実行し（import from derivation）、ホストごとの JSON を作る。JSON は、ホスト全体の NixOS の設定（利用者ごとの NixOS の設定を含む）と、利用者ごとの Home Manager の設定を持つ。手で実行する手順や、生成物の commit をなくすため。[confgen.nix](../../modules/home-manager/confgen.nix) と [NixOS 側](../../modules/nixos/confgen.nix) は JSON をそれぞれの設定にし、印（`$pkg`、`$exe`、`$concat`）をそのホストの `pkgs` の値に置き換える。

値（ホストの構成、`purposes`、ホストとユーザーの値）は TOML に置き、処理は要素に置く。flake は評価の最初に構成の一覧を決める必要があり、Nix が読めるのは Nix、JSON、TOML だけなので、ホストのファイルは TOML にした。flake（`lib/configurations.nix`）は `config/hosts/*.toml` から構成の名前、system、ユーザーを読み、confgen は同じファイルを要素に渡す。同じ値を2か所に書かなくて済む。

ホスト名、system、ユーザー名は、`lib/configurations.nix` が import するときに渡す。NixOS のモジュールはホストの JSON の全体を、Home Manager のモジュールはその利用者の部分を読む。`config` や module 引数の `pkgs` から決めると、設定の名前の一覧を決めるのに設定そのものが要り、無限再帰になる。confgen の build には specialArgs の `inputs` の nixpkgs を使う。

この build もほかの build と同じく、`nixos-spin713` ではデスクトップに回る。macOS の Home Manager 構成では aarch64-darwin の confgen を build するので、Linux の `check.sh` からは評価できない。Mac を使い始めるまで、そのホストのファイルを置いていない。

## 変更が影響する範囲

`confgen affected <repo-root> <変更ファイル>...` は1行の JSON `{"elements": [...], "hosts": [...]}` を返す。`elements` は変更した要素、その公開値を読む要素、書き込み先、派生条件にその要素を含む要素。`hosts` は、それらを生成する実在ホストの名前。ホスト・ユーザーの情報を変更した場合は、それぞれ `host`・`machines`・`user` への影響として扱う。要素から影響を辿れない変更は `elements = ["ALL"]` とする。

[scripts/check.sh](../../scripts/check.sh) はこの結果と各 check の札を照合して、ホストの評価とテストのビルドを選ぶ。札と実行範囲は [検証ガイド](../howtouse/validation.md#checksh) を参照。

## 今後の課題

- [ ] 任せる側の `remote_build` が、自分用サーバの機体の事実から `supportedFeatures` を作る仕組み。今は `remote_build.star` に `kvm` を定数で書いており、KVM のない機体を自分用サーバにすると、`kvm` を要求するビルドが実行時に失敗する。機体の事実は機体の要素だけから決まるので、confgen がほかのホストの機体の事実も `roles` と同じように渡せば、自分用サーバの機体に `local_kvm` があるかで決められる。
- [ ] 会社 PC の WSL に、自宅のマシンへの接続経路（`ssh_server`、`connect_ssh`、`tailscale`、`remote_build`、自分用サーバのクライアント）が入ったら生成を止める検査。今は検査がなく、`docs/architecture/wsl.md` の決まりは、WSL の機体の要素と利用者の `purposes` にこれらを書かないことで守っている。
