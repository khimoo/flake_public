# flake_public のあるべき姿

flake_public は、複数のホストの構成を、ユーザーが利用目的を選ぶだけで決められるようにする。
この文書は、そのための「2つの規則」と、規則を守れば何が解けるかを書く。
規則をツールでどう守らせるかは [confgen.md](confgen.md) に書く。

## 1. 課題

エディタの設定、SSH接続の設定、定期バックアップのタイマーなど、コンピュータの構成を形作るひとかたまりの単位を**コンポーネント**と呼ぶ。
ホストの構成は、複数のコンポーネントを組み合わせて組み立てられるが、数が増えるにつれて次の3つの問題が起きる。

1. **追加した理由が分からなくなる**
   動画編集のために追加した設定が、編集を行わなくなった後も残り続ける。残された設定だけを見ても、今も必要なのか不要なのかを判別できない。
2. **変更の影響範囲が追えない**
   ある設定が別の設定値を参照しているとき、その関係が明記されていないと、変更時にどこまで影響が及ぶかを一覧できない。
3. **関係性が個人の記憶に依存する**
   関係性を外部のスプレッドシート等にまとめても、構成定義との二重管理になり、やがて乖離して役に立たなくなる。

## 2. 考え方：依存関係から「十分条件」へ

コンピュータの構成を考えるとき、私たちは普段「依存関係」という言葉を使う。
しかし、私たちが普段そう呼んでいるものは、本当に「それがないと動かない必要条件」なのだろうか。

たとえば、あるプログラムの動作に特定のライブラリが必要だとされている場合でも、実際には別の互換ライブラリで代用できるかもしれないし、必要な関数だけを自分で書いてしまえば動くかもしれない。依存関係の一覧に特定のパッケージ名を書いた時点で、それは「これがあれば動く」という選び方の1つを指定しているにすぎない。

プログラミングや動画編集といった、ユーザーの利用目的を考えるときも同じである。「プログラミングをする」という目的に対して、エディタや git は本当に不可欠だろうか。極論を言えば、OS さえ必須ではない（かつて人類はパンチカードでもプログラミングを行っていた）。何が不可欠かは客観的には決まらない。

そこで、「何が必要か」を探すのではなく、定義者が**「これらが揃っていれば、プログラミング環境としてはこれで十分である」**と宣言するアプローチをとる。「エディタと git があるならば、プログラミングができる」という命題を立てたとき、それらが揃っていれば目的を達成できる要素の組（エディタと git）を、その利用目的の**十分条件**と呼ぶ。

ただし、ここで扱うのはアプリケーションの水準であり、ハードウェアや OS をどう構築するかという低い層までは掘り下げない。そこで、CPUアーキテクチャやOS、仮想化支援機構の有無といった、インストールでは変更できずホストごとに決まっている客観的な動作環境を**プラットフォームの事実**と呼び、そこより下は掘り下げない境界線とする。

したがって、コンポーネントの十分条件に書く要素は、次の2種類に整理される。

1. **他のコンポーネント**：ツールがインストールや設定によってホストに追加できるもの。
2. **プラットフォームの事実**：インストールでは用意できず、そのホストで最初から成り立っていなければならない環境の性質。

各コンポーネントは自身の十分条件として他のコンポーネントを並べることができ、この十分条件のつながりによって構成全体の有向グラフが形成される。

## 3. 構成要素と言葉

この構成管理の仕組みで用いる概念と言葉を整理する。

### 構成の単位

- **コンポーネント**：構成を組み立てる構成要素の単位。設定値を持つものと、他のコンポーネントを束ねるだけのものがある。
- **利用目的**：ユーザーがホストで達成したいこと（プログラミング、動画編集など）。ホスト上のユーザーごとに個別に選択する。利用目的自体もコンポーネントの一種であり、構成を決定する起点となる。
- **ハードウェアプロファイル**：ホストそのもの（物理マシンや仮想マシン）を表すコンポーネント。ホストごとに1つ割り当てられ、そのホストのプラットフォームの事実を保持する。全ユーザー共通の起点となる。
- **有効**、**ホストに入る**：特定のユーザーについて、コンポーネントが構成に含まれている状態を、そのユーザーについて「有効」であるという。また、ホスト上の誰か1人でも有効になったコンポーネントは「ホストに入る」という。
- **設定値**：インストールするパッケージ名や設定ファイルの記述など、具体的な設定項目。ホスト全体に適用される**システム設定**と、個々のユーザーに適用される**ユーザー設定**がある。

### データの受け渡し

- **公開値**：他のコンポーネントから参照されるために、コンポーネント定義の中で外部に向けて提供する名前付きデータ。
- **参照（読み取り）**：コンポーネントが、他のコンポーネントの公開値を取り出して自身の設定値を決定すること（pull型）。
- **寄与（送り込み）**：コンポーネントが相手に対してデータを送り込み、受け取った側がすべての寄与値を集約して自身の設定値を組み立てること（push型）。たとえば、各コンポーネントがパッケージ管理コンポーネントに必要なパッケージ名を送り、受け取った側が一括インストールする設定を作る。
- 参照は相手が提供する値を読み取るのに対し、寄与は相手に値を送り込んで集約させるという違いがある。

## 4. 構成を決定する2つの規則

ユーザーの操作は、ホストごとに、自身のユーザーアカウントについて「どの利用目的を選択するか」を指定することだけに限定される。
ツールは、以下の2つの原則に従ってホストの構成を決定する。

### 規則 A：コンポーネントがホストに入るか否か

1. ユーザーについてコンポーネントが有効になるのは、そのユーザーが選んだ利用目的、またはハードウェアプロファイルから、十分条件のつながりをたどって到達できるときに限られる。
2. 有効になったコンポーネントの十分条件に含まれるすべてのプラットフォームの事実は、そのホストで成り立たなければならない。1つでも成り立たない事実があれば、そのホストの構成は作られない（不適合なコンポーネントだけを黙って除外すると、選んだ利用目的の一部が気づかないうちに欠けた不完全な構成が作られてしまうため、ツールは安全のために処理を停止する）。
3. 少なくとも1人のユーザーで有効なコンポーネントだけがホストに入る（システム設定がホストに追加され、有効なユーザーにはユーザー設定も追加される）。
4. 設定値を持つコンポーネントは、有効になったら必ず1つ以上の設定値を追加しなければならない。コンポーネントは渡された値（ホスト名など）を読み取って設定値を計算できるが、特定の値に対して設定値を空にする条件分岐を許すと、十分条件のつながりではなく値のロジックがコンポーネントの有無を決めてしまう。この抜け道を塞ぐための制約である（他のコンポーネントを束ねるだけのコンポーネントはこの制約の対象外とする）。

### 規則 B：設定値を決定するもの
コンポーネントが追加する設定値は、以下の要素のみによって決定される。

- **ユーザー設定**：自身の定義、そのユーザーについて有効な他のコンポーネントから参照した値、および寄与された値。
- **システム設定**：自身の定義、ホストに入る（いずれかのユーザーで有効な）他のコンポーネントから参照・寄与された値。
- **外部入力の禁止**：定義ファイルから、環境変数、外部ファイル、時刻などを直接読み込むことはできない。
- **システム設定への制限**：システム設定の決定に、ユーザー名やホームディレクトリなど、ユーザーごとに異なる値、およびそれらから計算された値を含めることはできない。

### 組み合わせによる設定の扱い

規則 A と規則 B により、定義の中に「特定のホストなら」や「他のコンポーネントが入っているなら」といった条件分岐を書くことはできない。
したがって、「リモート接続経由でエディタを使うときだけ必要な設定」のように、複数の要素が揃って初めて必要になる設定は、条件分岐で解決するのではなく、「リモート環境でプログラミングを行う」という新しい利用目的を作り、その十分条件にエディタ、リモート接続、および追加設定コンポーネントの3つを並べて解決する。

## 5. 規則を守れば課題が解ける理由

- **理由が残り、不要な設定が消える（課題1の解決）**
  すべての設定は、利用目的から十分条件をたどった到達経路として記録される。利用目的を外せば、そこからしかたどれなくなったコンポーネントは自動的に無効化され、連動する設定値もホストから取り除かれる。使われなくなった設定が「なぜ残っているのか分からない」まま放置されることはない。

- **変更の影響範囲が追える（課題2の解決）**
  コンポーネント同士の関係性は、十分条件のつながりと、公開値の参照・寄与の宣言にすべて明記されている。あるコンポーネントを変更した際、その接続関係をたどった先にないコンポーネントには一切影響が及ばないため、変更前に影響範囲を確実に特定できる。

- **記憶に頼らない（課題3の解決）**
  構成の依存関係やデータの流れは、すべてコンポーネント定義のコードの中に完結している。外部のスプレッドシートを二重管理する必要も、誰かの記憶に頼る必要もない。

## 6. 保証の範囲

### 規則が保証しないこと

- **実行時の依存**：プログラムが実行中に別のコマンドを動的に呼び出すような関係（定義上のつながりには現れない）。
- **実行時に作られる状態**：アプリケーションのキャッシュや、実行時に生成される動的データ。
- **利用者のデータ**：コンポーネントが無効になった際、ユーザー自身が作成したデータまで消去するかどうか。
- **外部コンポーネントの内部挙動**：外部から取り込んだパッケージが、独自の初期設定で勝手に機能を有効化してしまうケース。

### 規則が決めないこと（定義者の判断に委ねるもの）

- **十分条件に何を並べるか**：必要なツールが欠けていれば動かず、余計なツールを並べれば不要な設定が入り続ける。
- **プラットフォームの事実に何を書くか**：環境の前提を書き忘れた場合、ツールの事前検査では停止できず、実機テストやビルド時に初めて失敗する。
- **全ホスト共通の設定をどこに書くか**：常に全員に入れたい基本設定であっても、利用目的またはハードウェアプロファイルの十分条件に明示的に並べる必要がある。

### 扱っていない課題

- [ ] **他ホストにまたがる設定の連動**：ラップトップのバックアップ先としてサーバ側のコンポーネントが存在する場合、ラップトップ側で利用目的を外しても、サーバ側の構成は自動では消えない（サーバ側で対応する利用目的を外す必要がある）。
