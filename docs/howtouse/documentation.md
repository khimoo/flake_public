# ドキュメントの整備

設計: [構成の境界](../architecture/configuration.md)
共通指示: [AGENTS.md](../../AGENTS.md)

人間とAIエージェントは同じドキュメントと手順を使用します。Claude Code では `/workflow <tool>` コマンドを、それ以外の環境では通常のドキュメント整備リクエストを通して本手順を利用できます。コマンドの明示的な実行は対象ドキュメントの編集依頼を意味します。なお、設定の編集はユーザーが事前に許可した範囲内でのみ行います。

## 対象の確認

対象の実装、既存の利用ガイド・設計ドキュメント、および各インデックスを確認し、用途、有効化条件、対応 OS、キー操作、設定の変更・反映手順、無効化・復旧手順を把握します。過去の記録だけで現在の挙動を断定せず、必ず実装と照合してください。確認できなかった点や未実装の案がある場合は、その旨を明記します。なお、確認した事項のうちドキュメントへ記載するのは、次節の基準を満たすもののみとします。

## 記載内容の選定

ドキュメントに残す情報は、将来の操作や判断に必要であり、再調査にコストがかかるものに限定します。

- **利用ガイド**: 操作手順を説明するドキュメントです。実行コマンド、変更対象の設定箇所、前提条件、正常終了の確認方法、エラー時に原因を調べるためのログや確認コマンドなどを、場面ごとに章分けして記述します。
- **設計ドキュメント**: 今後設定を変更する人が、現在の決定事項とその理由を把握するためのドキュメントです。現在の決定事項と、それを変更する前に知っておくべき理由を記載します。バージョンを特定して確認したアップストリームの挙動、ユーザーの選択事項、観測された事実など、再調査が困難な根拠も記録します。却下した案や見直しの条件は、実際に存在する場合のみ記載します。
- **記載しない内容**: コードを見ればわかる情報（設定ファイルの一覧、モジュールの役割、設定値の転記など）は記載しません。また、作業の経緯（過去の構成、日付付きの作業記録、検証・計測のプロセスなど）はコミットメッセージに記録します。

## 配置と参照の整理

- 利用ガイドや操作手順は [使い方ガイド](README.md) 配下に、採用理由・トレードオフ・根拠などは [設計判断](../architecture/README.md) 配下に配置します（小規模な機能については後述の例外を参照）。
- 関連する利用ガイドと設計ドキュメントを相互にリンクし、実装コードに対してはローカルリンクを設定します。ファイルの追加・削除に合わせてインデックスも更新してください。
- 設定ファイルを「挙動の正本」、詳細ドキュメントを「使い方および判断理由の解説」、インデックスを「案内・導線」として扱います。詳細な表や手順は一箇所のみに記載し、他のドキュメントへ重複して転記しないでください。コードコメントにはその箇所で必要な最小限の理由のみを書き、背景が長い場合は設計ドキュメントへのリンクを貼ります。
- 小規模な機能は単一の利用ガイドにまとめ、採用理由・却下案・トレードオフは同ドキュメント内の「設計」セクションに記述します。利用ガイドまたは設計内容が長くなり、一冊のドキュメントでは読みづらくなった場合は分割します。
- インデックスには、ドキュメントの目的のみを 1 文で簡潔に記述します。キー操作、手順、設定値、判断の結論や理由などの詳細は本体ドキュメントに記載し、インデックスには転記しないでください。
- ローカルメモリを規約やインデックスの正本とせず、判断の前提や見直し条件は共有される対象ドキュメント内に記録します。

## 確認と報告

検証作業は [検証ガイド](validation.md) に基づき、変更範囲に応じて適切な項目を選択して実施します。ただし、ユーザーから検証の省略が指定されている場合は、その指示に従います。

作業完了後、変更内容、確認結果、未確認・未検証の事項、およびユーザーによる適用や実機での動作確認が必要な箇所を報告します。
